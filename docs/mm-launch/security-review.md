## Inherited findings requiring an explicit decision

1. **Public privileged functions:** Supabase's SECURITY DEFINER exposure advisory remains applicable. Equality with preview and the passing actor checks do not establish every future call is safe. Production additionally grants PUBLIC EXECUTE to `is_tutor`, `enrolled_in`, `can_read_lesson` and `create_profile`; effective anon/authenticated permissions match preview. Smallest hardening proposal: remove only redundant PUBLIC grants and review the unnecessary direct trigger-function grants while retaining required application-role helper calls. This needs a separately reviewed exact privilege/rollback package and metadata-contract update; no blanket revoke or schema relocation is proposed during cutover.
2. **Broad table grants:** both app roles retain TRUNCATE on courses, enrolments, lesson_progress, lessons, modules, practice_attempts, profiles and questions. TRUNCATE is not governed by row policies. Metadata confirms the grants; these operations were not attempted against live data. No arbitrary-SQL/truncate REST endpoint was found in the reviewed public function set, and these are non-login roles, so this finding is not a demonstrated unauthenticated HTTP data-deletion exploit. Smallest proposal: review/remediate unused TRUNCATE/TRIGGER/REFERENCES privileges separately while preserving required SELECT/INSERT/UPDATE/DELETE and column grants. Do not silently declare all SQL-level boundaries safe because REST tests passed.
3. **Leaked-password protection:** the earlier provider advisory/settings limitation remains unverified for production. Preview recovery delivery success does not establish this protection. It requires a non-secret dashboard observation and supported-plan decision; no purchase or Auth policy change was made.
4. **Tutor-managed enrolment:** profile creation does not auto-enrol by year; local tests verify this remains true. Existing enrolment behavior is preserved. Any promise of automatic year access needs explicit owner acceptance or a separately scoped behavior change, not bootstrap SQL on production.

The `security_acceptance` and `enrolment_behavior` release gates remain unverified. The concrete evidence narrows the decision; it does not accept the risks on the owner's behalf or authorize production changes.
