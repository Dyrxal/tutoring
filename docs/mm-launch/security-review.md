# MM permission and privileged-function review — 7 November 2026

Scope: existing reviewed metadata, fresh read-only retained-project metadata/role inspection, static review of the 25 public function definitions, and [disposable synthetic database tests](../mm-acceptance/local-database-rehearsal.json). No production policy, role, data, password or private object was changed/read. This is a bounded migration review, not a complete penetration test or a claim that every RPC/argument combination is secure.

## Passing evidence

- Fresh production metadata matches the reviewed contract's effective app-role grants, policies, columns, constraints, triggers and definitions, except the already prepared four legacy conflict codes and four explicitly recorded PUBLIC ACL differences. No unexpected widening was found in this comparison.
- `anon` and `authenticated` are non-login roles, cannot bypass RLS, and cannot CREATE in public, confirmed by a production read-only role/schema privilege query. They can use the schema. The test harness assumes those same role properties; it does not grant clients arbitrary SQL access.
- The 25 public functions contain 21 SECURITY DEFINER functions. Read helpers derive actor identity from `auth.uid()`/`is_tutor()`/enrolment. Private review helpers and trigger functions have restricted EXECUTE; public mutation RPCs perform actor/enrolment/tutor checks, with the legacy flag wrapper delegating to the guarded shared function. Profile creation ignores a user-supplied role and defaults to student.
- The local original, prepared and restored states reject student role escalation, self-enrolment, spoofed tutor actions, cross-student review actions, private helper calls, another student's attempts and direct review-metadata inserts. Anonymous/unenrolled question and private-object reads return no rows. Tutor editing and enrolled access remain available. These are real local Postgres/RLS checks using synthetic records and minimal Auth/Storage stubs; prior hosted preview evidence remains separate.
- The exact prepared SQL preserves the full synthetic schema's owners/ACLs apart from its intended function-definition changes; rollback restores the original schema dump. Mismatched/repeated forward and rollback packages abort. Both review RPCs return legacy `40001` before the change and `PT409` after it and after restore for the tested missing-schedule case. Existing hosted review/retry/account-switch evidence covers additional cases; it was not rerun without a reason.

## Inherited findings requiring an explicit decision

1. **Public privileged functions:** Supabase's SECURITY DEFINER exposure advisory remains applicable. Equality with preview and the passing actor checks do not establish every future call is safe. Production additionally grants PUBLIC EXECUTE to `is_tutor`, `enrolled_in`, `can_read_lesson` and `create_profile`; effective anon/authenticated permissions match preview. Smallest hardening proposal: remove only redundant PUBLIC grants and review the unnecessary direct trigger-function grants while retaining required application-role helper calls. This needs a separately reviewed exact privilege/rollback package and metadata-contract update; no blanket revoke or schema relocation is proposed during cutover.
2. **Broad table grants:** both app roles retain TRUNCATE on courses, enrolments, lesson_progress, lessons, modules, practice_attempts, profiles and questions. TRUNCATE is not governed by row policies. Metadata confirms the grants; these operations were not attempted against live data. No arbitrary-SQL/truncate REST endpoint was found in the reviewed public function set, and these are non-login roles, so this finding is not a demonstrated unauthenticated HTTP data-deletion exploit. Smallest proposal: review/remediate unused TRUNCATE/TRIGGER/REFERENCES privileges separately while preserving required SELECT/INSERT/UPDATE/DELETE and column grants. Do not silently declare all SQL-level boundaries safe because REST tests passed.
3. **Leaked-password protection:** the earlier provider advisory/settings limitation remains unverified for production. Preview recovery delivery success does not establish this protection. It requires a non-secret dashboard observation and supported-plan decision; no purchase or Auth policy change was made.
4. **Tutor-managed enrolment:** profile creation does not auto-enrol by year; local tests verify this remains true. Existing enrolment behavior is preserved. Any promise of automatic year access needs explicit owner acceptance or a separately scoped behavior change, not bootstrap SQL on production.

The `security_acceptance` and `enrolment_behavior` release gates remain unverified. The concrete evidence narrows the decision; it does not accept the risks on the owner's behalf or authorize production changes. Retain the existing protected original definitions/grants and fresh baselines before any later approved hardening.
